# Proposal: evaluate a 384-token byte-BPE alternative

Status: proposed for review; no experiment or migration authorized by this document.
Date: 2026-10-10. Budget: one hour of elapsed work after approval, including reporting.

## Question and motivation

Would a standard, inspectable byte-level BPE tokenizer serve our tiny inference
instrument better than its current whole-word/hex codec, within **384 total IDs**?

The immediate symptom is concatenated generated words such as
`sisterbehindoflovejustbottle`. The current tokenizer represents spaces explicitly;
if the model does not select them, they are absent. That is not a round-trip bug.
Adding spaces in the UI or decoder would misrepresent the computation.

The experiment concerns representation cost and complexity. It cannot establish
that a different tokenizer teaches spacing or produces useful language. Those
are model-training questions. The project's priority remains inspectable inference,
including caching and state transfer; tokenizer work must justify its diversion
from those goals.

## Baseline and candidate

| | Current baseline | Proposed candidate |
| --- | --- | --- |
| Allocation | 352 words + 6 controls + space + 8 punctuation + BYTE + 16 hex digits | 256 bytes + 122 learned merges + 6 controls |
| Familiar words | Usually one ID, with separate spaces | May span several IDs; frequent pieces may include a space |
| Unfamiliar text | Each fallback UTF-8 byte costs three IDs | Each UTF-8 byte is directly representable before merges |
| Source preservation | Exact supported Unicode text, no normalization | Require the same preservation; no whitespace cleanup or normalization |
| Inspectability | Word pieces and explicit hex triplets | Byte pieces and their merge ancestry |

Baseline authority: [manifest and selection history](../../data/tokenizer/README.md)
and [codec implementation contract](../implementation/tokenizer.md).
The frozen number is token IDs, not words. Neither design enforces a closed
child-language lexicon or guarantees well-formed arbitrary generated text.

Reuse [Karpathy's minbpe](https://github.com/karpathy/minbpe), initially its
`RegexTokenizer`, pinned to an inspected upstream revision with its license
recorded. Document its exact pre-tokenization pattern and special-token handling.
Train 378 ordinary entries, then reserve six distinct control IDs. Feed message
text separately; do not learn merges across messages, roles, or record boundaries.
If the upstream training interface requires an adapter for this boundary, expose
and test that adapter rather than concatenating messages silently.

If the corpus cannot support 122 merges, report the shortfall; do not pad the
vocabulary with invented pieces or silently change the experiment. Inspect whether
the library's decoder replaces invalid UTF-8: lossless source round trips do not
make arbitrary generated byte streams valid. Retain raw bytes and report invalid
or incomplete sequences explicitly in diagnostics, without output repair.

Karpathy's [microGPT](https://karpathy.github.io/2026/02/12/microgpt/) uses 26 letters
plus BOS on names. nanoGPT's [character example](https://github.com/karpathy/nanoGPT/blob/master/data/shakespeare_char/prepare.py)
uses 65 observed characters, including whitespace; its
[BPE example](https://github.com/karpathy/nanoGPT/blob/master/data/shakespeare/prepare.py)
uses GPT-2 through tiktoken. These are references for mechanisms, not evidence
that BPE will win at our budget.

## Data and leakage controls

Before fitting, freeze the exact inputs, partitions, candidate settings, and
evaluation cases. Record source IDs, revision, and content identities in the
experiment evidence. Do not tune after inspecting evaluation results.

- Fit on the existing controlled **training** split and the separately exported
  language seed, each exported record once. Preserve existing exclusions and
  report the mixture's byte and record counts. See the [corpus recipe](../../data/corpus/README.md).
- Measure controlled development examples separately. They test combinations
  within familiar templates, not unseen language. Leave the model test split
  untouched so this spike does not consume that later evaluation.
- Report existing dialogue and vocabulary probes as historically informed
  diagnostics. Several influenced lexical selection; they are not independent
  held-out evidence. The baseline has a curation advantage on those cases.
- Freeze a small additional challenge set before fitting: ordinary sentences,
  contractions, case changes, unfamiliar names/words, accented text, another
  script, emoji, punctuation, repeated/leading/trailing spaces, tabs and newlines.
  Include literal joined words. These are authored counterexamples, not a
  representative sample of real users; report each case rather than broad claims.

No external corpus acquisition, data expansion, language-model training, vocabulary
size search, or architecture changes are included.

## Measurements and acceptance

Hard requirements, checked before interpreting efficiency:

1. Exactly 384 distinct IDs with six unambiguous framing controls.
2. Exact `decode(encode(text)) == text` for every evaluated source, including
   whitespace and non-ASCII cases; literal control-looking text remains text.
3. Deterministic fitting and encoding for fixed inputs/settings; no merges across
   declared message boundaries; evaluation inputs excluded from fitting.
4. Every token's bytes are inspectable, and learned pieces have reproducible merge
   ancestry. Include examples of space-bearing pieces if any are actually learned.
5. Malformed generated sequences remain visible as failures or incomplete bytes;
   no forced spaces, token masking, normalization, replacement, or output repair
   is presented as model output.

For each partition, report total tokens, median/p95/max per-example length, and
the paired candidate/baseline length ratio. Report content and full framed lengths
separately. Count examples exceeding the current declared context capacity without
truncating or excluding them. Show the worst regressions and improvements.

Also report fitting time and peak memory where available, a modest repeated
encoding/decoding timing with setup excluded, and integration complexity. These
local timings do not predict accelerator or production serving performance.
Do not compare lexical coverage percentages across incompatible token units.

**Successful spike:** a reproducible report supports retaining the baseline,
advancing BPE to a model comparison, or declaring the evidence inconclusive.
Retaining the baseline is a valid result. BPE eligibility requires all hard gates;
advancement additionally needs a documented tradeoff between ordinary-text cost,
fallback cost, context overflow, and implementation complexity. No aggregate
score or universal speedup claim: the intended workload weights are not established.
The owner reviews that tradeoff before any migration.

**Failure/incomplete:** any hard gate fails, inputs leak, results require repair,
or the time limit prevents a reproducible comparison. Preserve failures and stop;
do not weaken criteria, add candidates, or extend the deadline automatically.

## One-hour execution boundary and deliverables

| Elapsed allocation | Work |
| --- | --- |
| 0–15 minutes | Pin and inspect reuse; freeze data/cases and evaluation admission |
| 15–35 minutes | Fit one candidate; check round trips, controls, boundaries, determinism |
| 35–50 minutes | Measure paired lengths, context pressure, timing, and representative pieces |
| 50–60 minutes | Write findings, limitations, and recommendation, including unfinished work |

This is a work budget, not a predicted training duration. Stop at one hour even
if setup fails. Before implementation, register the criteria in the repository's
[evaluation admission](../../governance/evaluations.yaml). Any reusable declarations
must follow existing Tokenizer ownership; a research adapter is not a new runtime
tokenizer interface. The [Makefile](../../Makefile) remains workflow authority;
preparation checks stay outside the light inference test harness.

Deliver a maintained report and reproducible experiment source, with frozen
authored cases in a durable data location. Disposable fitted artifacts and detailed
measurements belong under `out/experiments/tokenizer-comparison/`. Do not change
the runtime codec, model artifacts, UI, or existing vocabulary during this spike.

## Possible follow-up: model comparison, separately reviewed

If justified, allow up to four hours for preparation, training comparisons, and
verification. This is not an estimate that training itself takes four hours:
the [first pilot](checkpoint-pilot-2026-10-09.md) recorded a 21.47-second training
loop for the current tiny architecture, excluding setup and verification.

Predeclare the next protocol after seeing sequence costs. Keep architecture,
precision, source examples, supervision, and generation policy controlled. Compare
matched source exposure and separately account for token positions, updates, and
compute: equal token budgets do not expose different tokenizers to equal text.
Report context overflow rather than silently truncating one candidate. Use multiple
seeds if affordable; a single run remains preliminary. Raw per-token loss is not
comparable across tokenizations; use text/task outcomes and a clearly defined
byte-normalized likelihood measure where applicable.

Changing token meanings requires new compatible model weights and regenerated
dataset encodings; retaining a 384-wide output does not preserve checkpoint
compatibility. Neither tokenizer alone guarantees readable random generation.

## Questions for the reviewer

- Is byte BPE worth this bounded comparison, or should we retain explicit spaces
  and spend the effort on the existing model's training/data instead?
- Is this fit/evaluation split honest enough given the baseline's curation history?
- Does the chosen pre-tokenization and boundary handling preserve the behavior
  needed for inspectable inference, without hiding Unicode or streaming failures?
- Are the measurements sufficient to decide on a follow-up, without inventing
  workload weights or optimizing merely for attractive output?
